# Схема данных

Артефакт лабораторной 4. Версия 1.0, 2026-11-23.
Файл `data/interim/incidents_clean_v1.0.csv`: 6 000 строк, 20 столбцов, кодировка UTF-8, разделитель — запятая.

## Единица анализа

Одна запись — карточка одного инцидента в ITSM: зарегистрированное событие с текстом, метками, временем и затронутой конфигурационной единицей.

Различать два уровня:

- **Инцидент** — карточка. Это единица анализа и единица оценки.
- **Событие** (`event_id`) — одно происшествие: одна-пять карточек, обычно внутри одного сценария. Двенадцать событий из 4 110 затрагивают два сервиса. Критичность и время начала общие для всех карточек события, поэтому независимыми наблюдениями они не считаются.

Одна карточка не равна алерту. В реальной системе один инцидент может собрать несколько алертов; в наборе одна карточка — это уже собранный инцидент, поэтому число записей не равно числу срабатываний мониторинга.

## Поля

| Поле | Тип и пример | Роль | Назначение |
|---|---|---|---|
| `incident_id` | `I000123` | аудит | Уникальный номер записи, присвоен после перемешивания |
| `scenario_id` | `SC-DB-01` | группировка | Сценарий отказа: сервис, симптом, категория причины. В признаки не входит |
| `event_id` | `E000123` | группировка | Событие: 1–5 карточек, 12 событий из 4 110 затрагивают два сервиса. В признаки не входит |
| `created_at` | `2026-09-14T12:05` | аудит | Время регистрации, ISO 8601 без часового пояса. Все времена условные |
| `source_system` | `Zabbix` | аудит | Система, из которой пришёл инцидент (7 значений) |
| `region` | `Москва` | аудит | Город из списка семи |
| `affected_ci` | `CI-483920` | аудит | Синтетический номер конфигурационной единицы, уникален в наборе |
| `title` | `Падает BGP-сессия с пирингом: BGP_Peers_Established=1 шт` | отображение | Заголовок карточки. В модель не входит |
| `description` | `Падает BGP-сессия с пирингом на host-msk017. BGP_Peers_Established держится 1 шт при пороге 2 шт. …` | признак | Единственный текст для TF-IDF и для поиска похожих |
| `language` | `ru`, `en` | аудит | Язык описания |
| `severity` | `P1`–`P4` | метка 1 | Критичность |
| `service` | `transport`, `platform`, `database`, `ims`, `billing`, `bss`, `external` | метка 2 | Затронутый сервис или домен |
| `root_cause` | `change`, `capacity`, `hardware`, `software`, `network`, `external_dep` | метка 3 | Категория корневой причины |
| `split` | `train`, `validation`, `test` | разделение | Назначение выборки |
| `rights_status` | `demo_allowed`, `unknown` | допуск | Внутренний статус технического примера |
| `synthetic` | `true` | маркировка | Признак синтетического происхождения |
| `source` | `generated:src/generate_incidents.py@1.0` | происхождение | Откуда взялась запись |
| `generator_version` | `1.0` | аудит | Версия генератора |
| `dataset_version` | `1.0` | аудит | Версия набора |
| `text_hash` | `3c0d06c6…` | группировка | SHA-256 нормализованного описания: поиск дублей и проверка split |

## Что используется для ранжирования

- Поиск похожих инцидентов (top-3) и классификаторы работают по `description`. `title` в модель не входит: заголовок короче и дублирует начало описания, включать оба — значит считать один и тот же сигнал дважды.
- `source_system`, `region`, `created_at` в версии 1.0 не используются. Семь систем мониторинга и семь регионов распределены почти равномерно, признак добавил бы шум, а не сигнал. Для реального архива решение пересматривается.
- `scenario_id`, `event_id` и `text_hash` — только разделение и проверки. Если пустить их в признаки, модель выучит метку по номеру сценария.

## Персональные и чувствительные данные

Персональных данных нет: ни имён, ни телефонов, ни адресов, ни номеров договоров, ни IP-адресов. Проверка автоматическая — тест `test_schema_is_complete_and_free_of_personal_fields` падает, если в схеме появится поле из чёрного списка (`email`, `phone`, `fio`, `login`, `passport`, `address`, `ip_address`).

Три поля, которые выглядят чувствительными и не являются:

- `affected_ci` — синтетический номер вида `CI-483920`. Реальной конфигурационной единице не соответствует, префикс сервис не кодирует: иначе метка `service` выучивалась бы по идентификатору.
- `region` — город из фиксированного списка, не адрес.
- `description` — вымышленные имена узлов (`host-msk017`) и метрики.

Коммерческой тайны нет: в наборе нет конфигураций, адресов оборудования и названий оператора. Остаточный риск относится к переносу, а не к текущему файлу: реальный текст инцидента может содержать внутренние имена сервисов и площадок, поэтому при появлении выгрузки нужна отдельная проверка на утечку инфраструктурных деталей.

## Связь с прежним черновиком

В `data/README.md` с лабораторной 1 лежал черновик схемы с 12 сервисами, 10 категориями причин и полями `monitoring_source`, `is_synthetic`, `resolution`. Версия 1.0 фиксирует другой набор:

- сервисы сведены к семи доменам, которые дают по 850–860 записей на класс;
- категории причин укрупнены до шести: при десяти категориях на 6 000 записей редкие получают меньше 300 примеров, и F1-macro по ним превращается в шум;
- `monitoring_source` переименован в `source_system`: источником бывает не только мониторинг, но и ITSM;
- `is_synthetic` стал `synthetic`, чтобы совпадал с маркировкой в курсовом образце;
- `resolution` убран: как решали инцидент, генератор не знает, а пустое поле в схеме хуже отсутствующего.

Расширение таксономии до `oss`, `monitoring`, `data_center`, `customer_portal` запланировано на версию 2.0 вместе с ростом объёма.
