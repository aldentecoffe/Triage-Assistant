# Data Card версии 1

Артефакт лабораторной 4. Дата: 2026-11-23. Версия набора: 1.0. Версия генератора: 1.0. Seed: 20261123.
Проект: ML-сервис автоматического триажа инцидентов для SRE-команды телеком-оператора.

## Назначение

Набор нужен, чтобы до появления реальных данных отработать техническую часть проекта: очистку, групповое разделение, обучение классификаторов критичности, сервиса и корневой причины, поиск похожих инцидентов. Вторая задача — сделать так, чтобы метрики можно было честно подписать: «на синтетическом наборе», без переноса на эксплуатацию.

Набор не заменяет пилот с дежурными инженерами и не измеряет продуктовые метрики (время до триажа, доля ошибочной маршрутизации). Для них нужен отдельный протокол с людьми, см. `docs/team-and-roles.md`.

## Создание

Записи сгенерированы скриптом `src/generate_incidents.py` по каталогу `src/incident_taxonomy.py`. Внешних изображений, архивов, API и сетевых запросов нет: набор воспроизводится из репозитория одной командой и не зависит от доступа к чужой коллекции.

Каждый сценарий задаёт сервис, категорию причины, две-три формулировки симптома, набор метрик с порогами и последствия для абонентов. Описание собирается из шаблона: симптом, значение метрики с порогом, последствие, номер конфигурационной единицы. Восемь записей испорчены намеренно: три дубликата текста, два пустых описания, три записи с `rights_status=unknown`.

Каскады: четыре пары сценариев, где одно происшествие даёт карточки в двух сервисах — например, потеря BGP-сессии и рост очереди записей о звонках в биллинге. Таких событий 12 из 4 110; остальные 4 098 приходятся на один сервис, 2 875 из них состоят из одной карточки. Критичность и время разыгрываются на событие, поэтому карточки одного происшествия не противоречат друг другу: разброс времени внутри события не больше 30 минут.

## Обработка

Порядок проверок фиксирован, чтобы причина исключения была однозначной.

| Стадия | Проверка | Исключено | Осталось |
|---|---|---|---|
| raw | — | — | 6 008 |
| 1 | `rights_status` не равен `demo_allowed` | 3 | 6 005 |
| 2 | описание пустое или короче 5 токенов | 2 | 6 003 |
| 3 | повтор `text_hash` (дубликат текста) | 3 | 6 000 |
| clean | — | всего 8 | 6 000 |

Порядок важен. Копии записей без подтверждённого допуска совпадают по тексту с оригиналами, а два пустых описания совпадают друг с другом по хешу пустой строки. Если проверять дубликаты первыми, отчёт показал бы восемь дубликатов и ноль записей без допуска, и причина исключения перестала бы быть понятной.

Журнал исключений: `data/interim/cleaning_log_v1.0.csv`, поля `incident_id`, `stage`, `reason`, `description`, `rights_status`. У записей, снятых первой проверкой, текст очищен: тот же скрипт по плану B пойдёт на реальную выгрузку, и хранить отклонённый по правам текст в отдельном файле нельзя.

Разделение на train, validation и test описано в [split_and_plan.md](split_and_plan.md). Группа — сценарий; он целиком попадает в одну выборку.

## Предполагаемое использование

- Отработка пайплайна: очистка, векторизация, обучение, оценка, анализ ошибок.
- Демонстрация сервиса на локальном наборе: три характеристики на инцидент плюс похожие инциденты.
- Сравнение подходов между собой на одинаковом разделении.

Не предполагается: оценка художественного качества, установление прав, сравнение с промышленными системами по абсолютным метрикам, выводы о реальной экономии времени дежурной смены.

## Репрезентативность

Сравнение с тем, как выглядит реальный поток инцидентов оператора.

| Сегмент | В наборе | Чего нет и почему это ограничение |
|---|---|---|
| Типы сервисов | 7 доменов с равными долями | Нет OSS-миграций, мониторинга, ЦОД, клиентского портала, партнёрских API и IoT/M2M. В реальном архиве распределение неровное: обычно доминируют два-три домена |
| Языки | Русский 79,6 %, английский 20,4 % | Нет смеси двух языков внутри одной карточки, транслита и жаргона дежурных («прод лежит», «деградация на транзите») |
| Авторы и команды | Семь команд-владельцев, по одной на сервис | Нет спорных инцидентов «ничей сервис», нет пересечения зон ответственности — а именно там модель чаще всего ошибается с маршрутизацией |
| Периоды | Август–ноябрь 2026, 110 дней | Нет сезонности: праздничные пики, массовые акции, плановые окна обслуживания, смена релизных циклов |
| Пользовательские сценарии | Только текст алерта | Нет вложений, комментариев в тикете, истории эскалаций, скриншотов и звонков — того, на что смотрит дежурный инженер |

Равные доли сервисов реалистичности не гарантируют. Набор специально устроен так, чтобы классов хватало для обучения; реальное распределение будет другим, и метрики на нём будут ниже.

## Ограничения

1. **Шаблонная генерация.** На сценарий две формулировки симптома, текст собирается из трёх шаблонов. Формулировки и имена метрик уникальны для сценария, а сценарий — это группа разделения, поэтому в test модель не видит знакомых слов и переносит только общий каркас фразы. Быстрый baseline на версии 1.0 (TF-IDF + линейная модель, обучение на train, оценка на test) даёт service F1-macro 0,3–0,6 и root_cause 0,1–0,2. Целевые значения проектного плана — service F1 ≥ 0,80 и root_cause ≥ 0,65 — на этой версии недостижимы. Коммитить модель с такими числами можно, выдавать их за качество сервиса — нет.
2. **Метки задаёт генератор, а не эксперт.** Согласие разметчиков не измерено, спорных случаев в наборе нет по построению. Для реальных данных нужна таксономия, согласованная с runbook, и проверка согласия.
3. **Сбалансированные сервисы.** По 14,3 % на домен — это удобно для обучения и не похоже на эксплуатацию.
4. **Критичность P1 — 6,9 %.** В реальной работе P1 встречается реже, обычно доли процента. Для обучения редкий класс полезнее частого, но абсолютные значения recall на реальном потоке будут ниже.
5. **Каскадов мало.** Четыре пары сценариев, 12 событий из двух сервисов из 4 110. Настоящий каскад затрагивает три-пять систем и растянут по времени.
6. **Английский — фиксированная доля.** 20,4 % заданы вероятностью, а не смешением команд и вендоров.
7. **Validation не покрывает категорию `network`.** Два сценария с этой причиной попали в train и test. Метрики на validation её не отражают, решение по категории принимается по кросс-валидации на train.
8. **Персональных данных нет, но риск переноса есть.** Текущий файл безопасен: имена узлов вымышлены, CI синтетические. Реальная выгрузка может содержать внутренние имена площадок и сервисов, поэтому перед её использованием нужна отдельная проверка.
9. **Продуктовые метрики набор не измеряет.** Приёмлемость подсказки, время до триажа и доля ошибочной маршрутизации требуют пилота с инженерами, а не синтетических данных.

## Ответственность

Автор проекта поддерживает генератор, каталог сценариев и схему, отвечает за версионирование и воспроизводимость. При появлении второго участника он берёт разметку golden set и ревью шкалы. За права на реальные источники отвечает владелец архива — оператор; без его письменного разрешения выгрузка в проект не попадает. Любое изменение состава, таксономии или разметки требует версии 2.0 и повторного расчёта всех метрик.
