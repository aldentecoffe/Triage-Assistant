# Карточка гипотезы и конфигурация запуска

Работа 9, эксперимент E01. Гипотеза перенесена из работы 8 без переформулировки: H1 и порог приёмки записаны в `docs/lab8/hypothesis.md` до появления кода этой работы. Меняется один фактор — порядок карточек внутри пула top-10.

## H1

Переранжирование пула top-10 по вероятности той же причины повысит NDCG@3 не меньше чем до 0,513 — то есть на 0,10 к baseline 0,413 — без падения защитных показателей.

## На какое наблюдение опирается

Механизм измерен в работе 8, а не придуман здесь. В 552 запросах из 1 200 ближайшая карточка той же услуги с другой причиной ближе, чем любая карточка той же причины: разница сигналов −0,175, средняя NDCG@3 у этой группы 0,233. Там, где ближе причина, — 498 запросов и NDCG@3 0,696. Корреляция разницы сигналов со средней NDCG@3 по семи сценариям — 0,86.

Второе наблюдение ограничивает притязания: медиана ранга лучшей карточки той же причины — 15, поэтому перестановка внутри top-10 упирается в потолок 0,544. Порог 0,513 лежит внутри потолка с запасом 0,031, и это делает проверку осмысленной: гипотеза может провалиться.

## Единственный изменяемый фактор

Сигнал сортировки. TF-IDF работы 6, индекс train, пул top-10, шкала релевантности v2.0, k = 3, набор запросов и tie-break остаются прежними. Baseline не удаляется: тот же прогон считает его тем же кодом, и его NDCG@3 0,413059 совпадает с опубликованной работой 8 до шестого знака.

Кандидат устроен так: на train обучается классификатор причины по тем же TF-IDF-векторам, затем каждый запрос получает вероятности шести причин. Внутри пула top-10 карточка сортируется по вероятности **своей** причины, при равенстве — по косинусу, затем по `incident_id`. Метки запроса в сортировку не попадают: функция `rerank_indices` получает только индексы пула, косинусы, идентификаторы и вероятности причин карточек, текста запроса у неё нет.

Перед фиксацией конфигурации на validation проверены четыре варианта сигнала: логистическая регрессия с выровненными весами (0,480), Complement NB (0,475), сходство с центроидом причины (0,471), логистическая регрессия без выравнивания (0,461). Ни один не достигает 0,513, поэтому отказ не объясняется неудачным выбором классификатора. Замер воспроизводится командой `python src/experiment.py variants` и записан в `results/variants.json`; выбран вариант с выровненными весами: в train `capacity` занимает 42,9 %, в validation — 14,3 %, и без выравнивания редкая причина не выигрывает у частой.

## Критерий положительного результата

NDCG@3 ≥ 0,513 **и** одновременно:

- попадание причины в top-3 у P1 не ниже baseline 0,062;
- NDCG@3 у P1 не ниже baseline 0,271;
- пустых выдач 0.

## Критерий отрицательного результата

Один порог, а не два: положительным считается только прирост не меньше 0,10. Зона 0,05–0,10 остаётся отказом, потому что такой прирост неотличим от разброса по сценариям. Гипотеза не подтверждена и при выполненных 0,10, если:

- защитный показатель по P1 ниже baseline;
- больше половины общего прироста даёт один сценарий.

Вторая проверка добавлена в карточке гипотезы работы 8 и здесь только реализована: средняя по набору складывается из трёх режимов выдачи, и перестановка внутри одного сценария ничего не говорит о системе.

Отдельного состояния «проверить дополнительно» нет: гипотеза бинарна, порог задан до прогона, и решение считается по правилу `expected_decision`, а не по усмотрению автора. Команда `freeze` отказывается записывать решение, расходящееся с условиями.

## Чем это не является

- Не проверкой полезности для настоящих дежурных: в измерении только метки, людей нет.
- Не доводом в пользу нейросети: если переранжирование не добирает, следующий шаг — другой фактор, а не «модель побольше».
- Не доказательством, что сигнал причины бесполезен: проверен один способ его получить на 3 600 карточках train.

## Риск и владелец

Риск: переранжировщик выучит частоту причины в train и начнёт подсовывать `capacity` вместо реальной причины. Владелец — ML-инженер проекта.

Защитный показатель P1 входит в условия решения. Точность классификатора по причинам — диагностика, а не формальное условие: порога для неё нет, классификатор раньше не оценивался. Диагностика читается вместе с вкладом по причинам: насыщение само по себе не говорит, откуда пришёл прирост; вклад каждой причины считается ниже.

По факту сигнал насыщен: argmax классификатора — `capacity` у 72 % запросов validation, `external_dep` не распознаётся ни разу. Но насыщение и вклад в прирост — разные вещи. Прирост распределён по причинам: `change` даёт 0,028 из 0,067, `capacity` — 0,015, `software` — 0,012, `hardware` — 0,009, `external_dep` — 0,003. То есть насыщение ограничивает интерпретацию сигнала, но не объясняет весь эффект; в решении это записано отдельным абзацем.

## Как воспроизвести

```
python src/experiment.py run
python src/experiment.py freeze --decision reject --reason "…"
python src/experiment.py test
python src/experiment.py variants
```

Первый прогон читает только train и validation. `freeze` проверяет решение по условиям и пишет отпечаток сводки. `test` отказывается работать без `freeze` и без совпадения отпечатка, поэтому test не может повлиять на выбор. `variants` — воспроизводимая запись выбора сигнала до фиксации конфигурации, на test не влияет.
