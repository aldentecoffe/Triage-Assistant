# Решение и допущения: ADR-01

## ADR-01, версия 1.0, статус «принято»

Контекст. Проект обещает три характеристики инцидента и top-3 похожих случаев
(ЛР 1). Поиск измерен в ЛР 7–9: NDCG@3 0,4131 по шкале v2.0, попадание услуги в
top-3 41,9 %, причины 38,6 %. Источника меток до ЛР 10 не было: частотный пол даёт
F1-macro 0,135 / 0,036 / 0,042, а классификатор причины существовал только как
переранжировщик и был отклонён решением ЛР 9. Цели плана: критичность 0,75 и P1
recall 0,90, услуга 0,80, причина 0,65, задержка меньше 1 с.

Решение. Alpha получает метки из трёх разных источников, каждый выбран по
измерению на validation:

| Метка | Источник | Почему он |
|---|---|---|
| Критичность | правило по таблице последствий; классификатор — только если фразы нет | 1,000 против 0,249 у модели; модель выдаёт только P2 и P3, ни одной P1 |
| Услуга | голосование по трём карточкам, которые инженер видит в ответе | 0,301 против 0,281 у классификатора, объяснение — сами карточки |
| Корневая причина | логистическая регрессия на TF-IDF | 0,266 против 0,205 у голосования |

Метка показывается без флага, если выполнено измеренное условие: для критичности —
найдена фраза последствия, для услуги — победитель собрал половину веса соседей.
Корневая причина всегда идёт с флагом «нужно решение инженера», потому что
условия, при котором она становится надёжнее, в измерении нет.

Один эндпоинт `POST /predict`, поля как в README проекта. Артефакт модели
сохраняется и загружается при старте, а не обучается на каждом запросе: обучение
трёх моделей и сборка индекса занимают около 0,7 с, полный проход — около 2,5 мс p95.

Рассмотренные варианты и почему отклонены:

- внешний LLM API — нарушает ворота о передаче текста за контур и о запуске без
  платного вызова, поэтому не сравнивается по качеству;
- локальные embeddings — не нарушают ворот, но модель не выбрана, качество,
  размер и задержка не измерены; это отдельный эксперимент, а не строка матрицы;
- классификатор для услуги — проигрывает голосованию 0,281 против 0,301 и хуже
  объясняется: вероятность не показывает, какие карточки привели к метке;
- голосование для причины — проигрывает классификатору 0,205 против 0,266.

Последствия. Хорошее: решение укладывается в 2,5 мс против бюджета 1 000 мс,
объяснимо без отдельного инструмента и не требует ни одной новой библиотеки.
Плохое: качество двух меток далеко от целей плана (0,301 против 0,80 и 0,266
против 0,65), и это ограничение придётся писать в README, а не прятать. Критичность
держится на правиле, то есть на определении метки, а не на модели.

«только в тестах», а не «используется».

## Окружение и запуск без платного API

Эталонное окружение: Windows 10, Python 3.12.10, scikit-learn 1.9.1, pandas 3.1.1,
NumPy 2.5.5. Оно записано в `results/check.json` и повторяет окружение ЛР 9.

Запуск не требует ключей, сети и загрузки моделей:

```bash
python src/generate_incidents.py --count 6000
python src/prepare_dataset.py
python src/split_dataset.py
python src/prepare_features.py
python src/arch_check.py run
python src/arch_check.py figure
```

Первые четыре команды строят набор из seed, следующие две считают измерение и
рисуют схему. Внешних вызовов нет ни в одной: генератор пишет синтетические
карточки, модель обучается на них же.

## Стоимость

Прямых расходов нет: ноль запросов к платным сервисам, ноль лицензионных платежей,
все пакеты под свободными лицензиями. Стоимость машинного времени, электричества и
труда в проекте не измерялась, поэтому в отчёте её нет — вместо нуля стоит
«не измерялась».

## Допущения и триггеры пересмотра

| Допущение | Что сломает решение |
|---|---|
| каталог мал: 3 600 карточек, десятки тысяч в пределе | больше 50 000 карточек, поиск по изображениям или логам — нужен другой индекс |
| тексты короткие, русский и английский, одна таксономия | новый язык или свободные описания без фраз последствий: правило перестанет находить критичность |
| критичность выводится из формулировки последствия | на реальных карточках доля найденных фраз ниже 80 % — правило нужно заменить |
| синтетика даёт перенос на реальные карточки | первая реальная выборка: все числа переизмеряются, цели пересматриваются |
| инженер готов подтверждать или править метку | доля правок выше половины: метка бесполезна и её надо убирать из ответа |
| задержка на CPU укладывается в бюджет | p95 выше 1 000 мс на целевом железе: тогда артефакт и кэш пересматриваются |

## Plan B

Если классификатор причины недоступен или его файл повреждён, сервис переходит в
`status=fallback`: отдаёт top-3 карточки и пустые метки. Если недоступен индекс,
возвращается 503, и инженер идёт в ручной просмотр истории.

Если решение по составу меток придётся отменять, второй по качеству набор — только
голосование: услуга 0,301, причина 0,205, критичность 0,419. Он измерен на тех же
1 200 карточках, поэтому переход не требует нового эксперимента, но теряет 0,061
F1 по причине и всю вероятность.

## Известные ограничения

- Услуга 0,301 и причина 0,266 против целей 0,80 и 0,65. Ни один измеренный
  вариант не приближается к цели, поэтому ограничение записано здесь и в README.
- Критичность 1,000 на синтетике не доказывает качество: метка выведена из той же
  таблицы, по которой работает правило.
- Все 96 карточек P1 относятся к одному сценарию SC-IMS-03; recall P1 на других
  формулировках не измерен.
- Причины `network` в validation нет ни одной карточки, её F1 равен нулю по
  построению.
- Test израсходован в ЛР 9 как контроль после замороженного решения. Второй запуск
  на test не был бы независимой проверкой, поэтому ЛР 10 test не читает.
- Метрики ЛР 2 (время до триажа, доля ошибочной маршрутизации) на синтетике не
  измеряются: в проекте нет дежурного инженера.
- Числа на validation оптимистичны. На пуле 14 сценариев train (leave-one-scenario-out)
  услуга даёт 0,087, причина 0,111 против 0,301 и 0,266 здесь, а сценарии validation
  ближе к истории по словарю (0,256 против 0,157). Поэтому выбор модели причины на
  этом пуле не подтверждается: голосование там выше на 0,026. Решение оставлено по
  validation — split отбора объявлен заранее, — а расхождение записано как
  ограничение. Разбор: `docs/diagnostics/scenario_cv.md`.

## Самопроверка

Самое рискованное допущение — что числа на синтетическом наборе хоть что-то
говорят о реальных карточках. Набор собран из 750 шаблонов, ни один шаблон не
пересекает выборки, а метка критичности выведена правилом генератора. Модель,
обученная на таком наборе, измеряет перенос на незнакомые шаблоны, а не понимание
инцидента.

Alpha проверит это тремя дешёвыми способами, все три входят в её интерфейс:
доля карточек, где правило нашло фразу последствия (поле `basis`), доля запросов с
флагом «нужно решение инженера» и доля правок в журнале обратной связи. Если первая
окажется низкой, вторая почти всегда true, а третья выше половины, значит метки не
работают, и это будет видно из ответа сервиса, а не только из отчёта.
