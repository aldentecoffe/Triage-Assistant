# Спецификация метрик

Работа 8. Запрос — карточка инцидента из validation, выдача — три похожих инцидента из train. Числа прогона — в `results/summary.json`, разрезы — в `segments.md`.

## Что измеряем и зачем

Дежурный открывает три похожих инцидента и по ним выбирает runbook. Значит, полезность определяется тем, попала ли в тройку карточка с той же причиной: услуга подсказывает владельца, а причину дежурный и так знает из системы мониторинга к моменту, когда смотрит подсказку.

Отсюда главная метрика — **NDCG@3 по причине**, а не точность и не F1. Accuracy по классу причины отвечает на вопрос «угадал ли ярлык», хотя пользователь не берёт ярлык из системы поиска; ему нужно, чтобы похожий случай оказался на первом экране. NDCG учитывает и попадание, и место: карточка с той же причиной на первом месте стоит дороже той же карточки на третьем.

## Шкала релевантности v2.0

| Оценка | Условие | Почему так |
|---|---|---|
| 2 | та же `root_cause`, услуга любая | такая карточка даёт runbook и модель отказа |
| 1 | та же `service` при другой причине | сосед по услуге полезен для контекста, но runbook не даёт |
| 0 | ни того, ни другого | карточка занимает место в тройке без пользы |

Шкала v1.0 из работы 7 требовала совпадения обеих меток для оценки 2. В этом разбиении пара «услуга + причина» не повторяется между train и validation: 14 пар в индексе, 7 у запросов, общих нет. Значит, оценка 2 в v1.0 была недостижима, NDCG делился на идеал из трёх оценок 1, и метрика измеряла «попал ли сосед по услуге», то есть ровно то, что нам не нужно.

Замена сделана не для того, чтобы поднять цифру. Шкала v2.0 строже: идеал стал [2, 2, 2] вместо [1, 1, 1], поэтому NDCG@3 упал с 0,629 до 0,413 при неизменной выдаче. Направление изменения видно на сегменте «какой сигнал ближе»: по v1.0 группы `service_closer` и `cause_closer` почти не различались (`0,675` и `0,708`, разница 0,033), по v2.0 они расходятся втрое (`0,233` и `0,696`). Старая шкала засчитывала совпадение по услуге как полезное и тем самым скрывала именно тот провал, ради которого метрика вводится.

**Обе шкалы остаются в отчётах.** Колонка «NDCG@3 по шкале ЛР 7» в `segments.md` нужна для сверки с опубликованными метриками baseline; сравнивать два столбца между собой нельзя.

## Параметры

| Параметр | Значение |
|---|---|
| k | 3 |
| Единица оценки | запрос, 1 200 карточек validation |
| Индекс | 3 600 карточек train, test не используется |
| Gain | `2**оценка - 1` |
| Дисконт | `1 / log2(позиция + 1)`, позиции с единицы |
| Идеал | три оценки 2 для каждого запроса (однороден у всех 1 200) |
| Равные сходства | сортировка по `incident_id` по возрастанию |
| Случайность | не используется, seed не задан |

## Правило пустой выдачи

Пустая выдача получает NDCG, Recall и MRR, равные нулю, и попадает в отдельный столбец «Пустых». Ноль не среднее и не ошибка: это видимый провал, и его нельзя прятать. В validation пустых выдач 0 из 1 200; правило проверено тестом на пустой строке, на запросе без общих с индексом слов и на `k = 0`.

## Правило запроса без релевантных объектов

Если бы у запроса в индексе не было ни одной карточки с оценкой 2 или 1, он **исключается** из среднего и считается отдельно строкой «Нет релевантных объектов»: их число попадает в `summary.json` и в `segments.md`, а знаменатель средней уменьшается на это число. Ноль в среднем смешал бы два разных факта: «система не нашла» и «искать было нечего».

Правило реализовано в `aggregate` проверкой `ideal_v2 > 0` и закрыто тестом на мини-корпусе, где у запроса нет ни карточки той же причины, ни карточки той же услуги. В этом наборе таких запросов нет: у каждого запроса в train есть сотни карточек той же причины, поэтому идеал однороден и средняя от правила не изменилась. Правило записано заранее, потому что при следующей версии данных или при смене таксономии такие запросы появятся, и решение нельзя будет принимать по результату.

## Порог приёмки

Порог задан правилом, а не числом, чтобы его нельзя было подогнать после прогона:

- **α = NDCG@3 baseline + 0,10**, то есть 0,513 при текущем baseline 0,413. Порог пересчитывается вместе с baseline: если baseline изменится, α сдвинется, а требование «плюс десять пунктов» останется.
- **Защитные показатели не ниже baseline**: попадание причины в top-3 у P1 (0,062), NDCG@3 у P1 (0,271), пустых выдач 0. Падение любого из них отменяет прирост главной метрики, даже если та выросла.

Запас есть: идеальная сортировка пула top-10 даёт 0,544, top-50 — 0,660. То есть α достижим без новой модели данных, но не бесплатно: переставлять карточки внутри top-3 почти бесполезно (`0,433`), нужен более широкий пул.

## Защитные показатели и почему именно они

| Показатель | Порог | Что защищает |
|---|---|---|
| Попадание причины в top-3 у P1 | ≥ 0,062 | самое дорогое: дежурный берёт чужой runbook в критичном инциденте |
| NDCG@3 у P1 | ≥ 0,271 | то же, но с учётом места, а не только факта попадания |
| Пустых выдач | 0 | отказ системы выглядит как ошибка ввода, а не как отсутствие данных |
| Классификация: F1-macro severity / service / root_cause | ≥ 0,135 / 0,036 / 0,042 | второй выход системы; пороги перенесены из работы 7 и в этой работе не пересчитываются |

Первые три показателя считаются в `summary.json` при каждом прогоне. Строка про классификацию — перенесённый порог: работа 8 оценивает поиск, а частотный классификатор остался в работе 7. Проверять его будет работа 9 вместе с матрицей ошибок по причине, иначе получится порог без владельца измерения.

Оговорка про P1 обязательна. Все 96 карточек P1 в validation — это один сценарий SC-IMS-03 (услуга ims, причина software), в котором 171 карточка; услуга ближе причины на 0,23 в среднем по сценарию и на 0,25 внутри самих карточек P1. Защитный показатель по P1 сейчас измеряет знакомство с лексикой этого сценария, а не поведение на серьёзных инцидентах. Порог оставлен, потому что это единственный доступный сегмент P1; ограничение записано в `value_link.md` и переносится в Data Card.

## Что эти метрики не измеряют

- Удобство интерфейса и время до выбора: продуктовая цель «пять минут» этой таблицей не проверяется.
- Права на контент и допустимость выдачи: в проекте синтетические данные, фильтра допуска нет.
- Поведение на реальных инцидентах: настоящих дежурных в измерении не было.
- Стоимость ошибки в деньгах: ущерб описан механизмом (чужой runbook), а не рублями.

## Как воспроизвести

```
python src/eval_report.py run
```

Модуль пишет `results/per_query.csv`, `results/overall.csv`, `results/errors.csv`, `results/summary.json`, `results/manual_case.json` и три документа: `segments.md`, `error_taxonomy.md`, `manual_calculation.md`. Два прогона дают побайтово одинаковые файлы. Перед расчётом модуль сверяет отпечаток словаря с `docs/lab6/features_manifest.json` и падает при расхождении: признаки работы 6 не должны меняться незаметно.
