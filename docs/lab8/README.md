# ЛР 8: метрики и анализ ошибок

Система показателей для поиска похожих инцидентов и разбор того, где baseline ломается. Опирается на baseline работы 7 и меняет только одно — шкалу релевантности, без которой метрика измеряла не то.

## Запуск

Из корня репозитория, после пайплайна данных:

```bash
python src/prepare_dataset.py
python src/split_dataset.py
python src/prepare_features.py
python src/eval_report.py run
```

Прогон занимает около 15 секунд, печатает сводку и пишет `results/per_query.csv`, `results/overall.csv`, `results/errors.csv`, `results/summary.json`, `results/manual_case.json`, а также `segments.md`, `error_taxonomy.md` и `manual_calculation.md`. Повторный запуск на тех же данных даёт те же файлы. `--results-dir` меняет каталог машинных файлов, тексты при этом пишутся в его родительский каталог.

Один запрос в том виде, в каком его считает отчёт:

```bash
python src/eval_report.py case --query-id I000280
```

## Что сделано

Шкала релевантности v2.0. Оценка 2 — та же причина (услуга любая), 1 — та же услуга при другой причине, 0 — ни того, ни другого. Старая шкала работы 7 требовала обеих меток для оценки 2, но пары «услуга + причина» не повторяются между train и validation, поэтому оценка 2 была недостижима, а NDCG делился на идеал из трёх оценок 1. Разбор — в [metric_spec.md](metric_spec.md).

Порог приёмки задан правилом: α = NDCG@3 baseline + 0,10 = 0,513. Защитные показатели — попадание причины в top-3 у P1, NDCG@3 у P1 и отсутствие пустых выдач — не ниже baseline. Правило записано до прогона, поэтому порог не подгонялся под результат.

Разрезы. Запросы делятся по языку, покрытию словаря, серьёзности, сценарию, каскаду и по тому, какой сигнал ближе — причина или услуга. Последний разрез и оказался главным.

Таксономия ошибок. Десять типов с числителем и знаменателем, примером, проверенной причиной и следующим шагом; семь из них относятся к основной выборке, три — к данным и коду. Собрана модулем из `results/errors.csv`.

## Результаты

По шкале v2.0 NDCG@3 0,413 против 0,629 по шкале работы 7 при той же выдаче. Падение — не регресс, а следствие того, что идеал стал [2, 2, 2] вместо [1, 1, 1].

Средняя метрика складывается из трёх режимов выдачи: 277 запросов получают три карточки той же причины (NDCG@3 1,000), 298 — три карточки той же услуги с другой причиной (0,333), 322 — три карточки без единой метки (0,000). Это не смесь удач и промахов, а три разных поведения ранжировщика.

Главный механизм измерен. У 552 запросов из 1 200 ближайшая карточка той же услуги ближе, чем любая карточка той же причины; разница сигналов −0,175, NDCG@3 у этой группы 0,233. Там, где ближе причина, — 498 запросов и 0,696. По семи сценариям разница сигналов и средняя NDCG@3 коррелируют на 0,86, по отдельным запросам — на 0,51.

Сегмент P1 оказался не сегментом: все 96 карточек P1 в validation — это один сценарий SC-IMS-03 (услуга `ims`, причина `software`), где услуга ближе причины на 0,23. Защитная метрика по P1 сейчас измеряет знакомство с этой лексикой, а не поведение на серьёзных инцидентах.

Потолок переранжирования: идеальная сортировка пула top-10 даёт 0,544, top-50 — 0,660. Медиана ранга лучшей карточки той же причины — 15, то есть нужное обычно рядом, но ниже отсечения.

Гипотеза для работы 9: переранжирование пула top-10 по вероятности причины, цель — NDCG@3 ≥ 0,513. Карточка — в [hypothesis.md](hypothesis.md).

## Что осталось непроверенным

- Чистка служебных слов и чисел. Измерено: у 189 запросов они дают больше половины косинуса, но доля шума не отделяет провал от успеха — 0,297 в самом шумном сегменте против 0,298 в самом чистом, а средний сегмент выше обоих (0,561) из-за разного состава режимов выдачи. Гипотезой не выбрана, из таксономии не убрана.
- Лемматизация. Не выбрана, потому что меняет представление, а не соотношение сигналов: запросы знакомы словарю (покрытие содержательных слов 0,154–0,667 при медиане 0,500 по работе 7, запросов без единого известного слова нет), а провал сосредоточен в сценариях, где услуга ближе причины.
- Доверительные интервалы. Числа точечные; 1 200 запросов — это 7 сценариев, поэтому разброс между ними важнее средней.

## Отличие от работы 7

Работа 7 публикует метрики по шкале v1.0 и остаётся как есть: её числа и правила не переписаны, обе шкалы показаны рядом в `segments.md`. Работа 8 не обучает новую модель и не меняет выдачу — только оценивает её иначе и разбирает результат по сегментам.
