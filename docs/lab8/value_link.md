# Связь с требованиями и ценностью

## Требования проекта

В методичке связь ведётся с «R из ЛР 3». В этом проекте работа 3 — учебный ноутбук по Wine Quality на чужих данных, поэтому своих R там нет. Вместо них взяты требования из проектного плана (работа 1) и проверок преподавателя; нумерация локальная и не ссылается на чужой артефакт.

| ID | Требование | Источник |
|---|---|---|
| R1 | Сервис возвращает минимум две характеристики объекта: `severity`, `service`, `root_cause` и top-3 похожих инцидентов | проверка преподавателя, план работы 1 |
| R2 | Решение рекомендательное: дежурный принимает окончательное решение сам | план работы 1, ограничения |
| R3 | Классификация критичности: recall по P1 не ниже 0,90 | план работы 1, таблица целевых метрик |
| R4 | Поиск не предлагает чужой runbook первым для P1 | введено в этой работе из разбора ошибок, не из плана |
| R5 | Ответ на один инцидент быстрее секунды | план работы 1 |

R3 и R4 — разные требования, и путать их нельзя. R3 относится к классификатору критичности: его recall по P1 в частотном baseline равен 0,00, потому что константа P3 не угадывает P1 ни разу. R4 относится к поиску: там проверяется, попала ли в top-3 карточка с той же причиной у P1. В этой работе измерено только R4; R3 остаётся за работой 9, где появится модель классификации.

## Что считается недопустимой ошибкой

| Ошибка | Почему недопустима | Замечается по | Сейчас |
|---|---|---|---|
| P1 с чужой причиной на первом месте | дежурный ночью берёт первый ответ и открывает не тот runbook; цена — минуты простоя и неверные действия | защитная метрика (R4): NDCG@3 у P1 и попадание причины в top-3 у P1 | 6 из 96 попаданий причины в top-3 |
| Пустая выдача | выглядит как ошибка ввода, а не как отсутствие данных; пользователь не понимает, что делать | столбец «Пустых» по всем сегментам | 0 из 1 200 |
| Три карточки без единой метки | пользователь получает три случайных инцидента и теряет доверие к подсказке | режим выдачи «0,0,0» | 322 из 1 200 |
| Причина ниже третьего места при наличии | подсказка формально есть, но её никто не листает | NDCG@3 против Recall@3 | MRR@3 0,674 |

R4 сейчас не выполняется: попадание причины в top-3 у P1 — 6,25 %, это 6 карточек из 96. Но за цифрой стоит один сценарий SC-IMS-03, поэтому требование нельзя ни закрыть, ни окончательно провалить: нужен сегмент P1 из нескольких сценариев, а это правка генератора, а не модели. R3 в этой работе не измерялся и остаётся открытым.

## Что допустимо в alpha

| Допущение | Условие, при котором оно честное | Чем ограничено |
|---|---|---|
| Причина на втором-третьем месте вместо первого | пользователь видит все три карточки сразу, порядок экономит время, но не меняет факт | MRR@3 0,674 |
| Сосед по услуге в тройке | он объясняет контекст и владельца, даже если runbook другой | доля «обе метки» 0,073 |
| Разрыв en и ru: 0,545 против 0,376 | пользователь видит язык карточки и может переформулировать запрос | в корпусе en-шаблоны короче, это свойство генератора |
| Разрыв между сценариями: 0,147–0,803 | ограничение записано в Data Card и в README, подсказка не подаётся как гарантия | по сути это свойство синтетических шаблонов |

Разрыв по языку и по сценариям допустим только с оговоркой: он показывает, что система неоднородна, а не что она «почти работает». Средняя 0,413 по всем запросам это скрывает.

## Связь с продуктовой целью

План обещает сократить время до выбора до пяти минут. Эта таблица такую величину не измеряет и не может: в ней нет людей. Метрики описывают только один шаг — нашлась ли карточка с нужной причиной среди трёх. Утверждение «быстрее в пять раз» остаётся гипотезой до замера на дежурных, и в отчётах проекта оно так и помечено.

## Владельцы рисков

| Риск | Владелец | Как проверяется |
|---|---|---|
| Чужой runbook на первом месте у P1 | ML-инженер проекта | защитные метрики в работе 9, матрица ошибок по причине |
| Переобучение на частоту причины в train (`capacity` 42,9 % против 14,3 % в validation) | ML-инженер проекта | отчёт по классам, а не только средняя метрика |
| Пользователь верит подсказке больше, чем проверке | заказчик (принимает продукт) | формулировка интерфейса: «похожие инциденты», а не «причина» |
| Синтетические шаблоны не описывают реальные инциденты | заказчик | сравнение на публичном корпусе IT-тикетов, отдельный шаг |
